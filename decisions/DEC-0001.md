## Decision
CloudCLI 使用的 `ANTHROPIC_API_KEY`（`/home/admin/files/projects/claude-ui/.env`）必须与 headroom 代理当前上游供应商的 token（`~/.config/headroom/proxy.env` 中的 `ANTHROPIC_AUTH_TOKEN`）保持一致。当切换 headroom 上游供应商时，同步更新 CloudCLI `.env` 中的 key 并重启 `cloudcli.service`。

## Options Considered

| Option | Pros | Cons |
|--------|------|------|
| A. 继续使用独立的 headroom 本地 API key（旧 `4fa71b63...`） | 与上游 token 解耦，理论上可单独轮换 | 该 key 已过期，Kimi 返回 401；当前 headroom 实际把客户端 key 透传给上游，无法独立存活 |
| B. 让 CloudCLI 直接使用上游供应商 token（Kimi token） | 立即修复 401，与 headroom 配置同源，减少 key 数量 | 切换供应商时必须同步更新 CloudCLI `.env` |

## Rationale
- 直接 curl 测试证明：旧 key → headroom → Kimi 401；当前 Kimi token → headroom → Kimi 200。
- CloudCLI 通过 Claude SDK 子进程发起请求，`sdkOptions.env = { ...process.env }` 会把父进程 `.env` 中的 `ANTHROPIC_API_KEY` 传给子进程。
- headroom 当前行为是把请求原样转发到上游，Authorization header 中的 key 必须在上游有效。
- 选择方案 B，因为方案 A 在当前架构下不可行。

## Expected Outcome
- CloudCLI 不再出现 401 认证错误。
- 切换供应商时，headroom 配置与 CloudCLI 配置同步变更，避免再次断链。

## Context
- 现象：CloudCLI 前端报错 "API Error: 401 The API Key appears to be invalid"。
- 动作：替换 `.env` 中 `ANTHROPIC_API_KEY` 为当前 Kimi token，重启 `cloudcli.service`，并通过 REST + WebSocket 端到端验证。
- 相关文件：`/home/admin/files/projects/claude-ui/.env`、`/home/admin/.config/headroom/proxy.env`。
